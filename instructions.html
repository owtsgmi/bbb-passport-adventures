👽 Passport Adventures

How our two-player passport game works

📖 How to Play

This is a lightweight two-person game built around BBB Passport stamp collecting in Second Life. Pick a three-stop adventure, travel together, collect stamps, and finish the whole trio on both passports.

For now, this game is strictly for 2 players. Both players use the same Secret Club Code so the private settings can sync between their devices. Do not share that code with anyone else.

1. Set up both players

1
Open Settings on the Adventures page.
2
Enter each player's actual Second Life username. Those usernames become the two player tabs.
3
Add each player's BBB StaFi progress-page link.
4
Use the same Secret Club Code on both devices.

Use usernames, not display names or nicknames. The Secret Club Code is only needed on trusted devices to load the private BBB StaFi links.

2. Pick an adventure

Tap ✨ Pick an Adventure. Each adventure has exactly 3 passport stops.

The current adventure stays pinned at the top so you can jump back to it easily while you're moving around Second Life. It is locked by default so an accidental tap on Pick an Adventure or another adventure cannot replace it.

To intentionally switch, uncheck Adventure locked on the Current Adventure bar. The app will still ask for confirmation before replacing it, and the newly selected adventure locks itself automatically.

Use Copy destination or the individual Firestorm copy buttons to get each location. Passport Adventures also shows the original BBB location photo beside each stop when the BBB catalog provides one.

A zoomable Second Life map appears at the bottom of the current adventure and marks all three stops. Use Fit to frame the adventure or World to zoom out across the broader Second Life grid. Every stop in the current adventure is selectable: click the stop row or its 🎯 Focus button to reset any previous pan/zoom and jump the map back to region-level detail for that stop.

3. Both passports must finish

One person can get ahead, but the adventure is not complete until both players have all three stamps.

If KK finishes first, the game should show that she is waiting on AA. The adventure does not jointly complete until AA catches up.

The NEXT marker points to the first stop that the app has not recorded as complete for both players. Once automatic StaFi importing is fully connected, an accepted BBB stamp should update that state and advance NEXT automatically. At the moment, saving a StaFi link does not yet provide that live stamp import.

4. Mystery L$ reward

When Adventure Treasure is enabled, each jointly completed three-stop adventure reveals a random 20–100 L$ prize for the second player.

The amount stays completely hidden while the adventure is in progress. It is generated once when both passports finish all three stops, then saved so reopening the app or switching devices cannot reroll it.

5. L$ adventure treasure

Each jointly completed adventure adds a hidden 20–100 L$ prize to the benefactor's Adventure Treasure.

Adventure Treasure is optional and off by default. An admin can turn it on from the Admin page. When it is off, players see no L$ treasure balance, mystery-L$ labels, or reward milestones.

When Adventure Treasure is on, the normal Adventures page keeps it fun and simple: the benefactor sees how much L$ is waiting for them, recent prizes, and progress toward the next 1,000 L$ milestone.

Payment reminders, browser notification setup, Pay shortcuts, and payment bookkeeping are intentionally kept off the player screen. Those live on the separate Admin page.

6. Passport progress

The top stamp counter is meant to show the whole passport total, not only the adventure subset.

Example: 1 / 382 stamps · 381 to go.

Automatic StaFi stamp importing is still being connected. Saving the StaFi link currently saves the private setting; it does not yet mean BBB progress has been imported.

Current two-player limitation: the shared state, Secret Club Code workflow, reward ownership, and payout logic are currently designed for exactly two people. A future public/shared version can support more players, but this version should be treated as a private two-person club.

🏗 App Architecture

A plain-English map of how Passport Adventures works today. This section is intentionally kept as living documentation for users and for future development.
GitHub Pages UI→Supabase shared state↔2 players+BBB live catalog

Front end

The app is a static GitHub Pages site built from plain HTML, CSS, and JavaScript.

  • Adventures: the shared two-player game board with a deliberately simple player-facing header.
  • Admin: setup, Adventure Treasure controls, notifications, and payout bookkeeping.
  • Instructions: user guide plus this architecture reference.
  • BBB Stops: searchable live-aware stop catalog, nearby-stop tools, images, and Second Life map display.
  • Comments & Bugs: public suggestions and bug reports.

Game data

The core adventure set is a stable snapshot of 381 campaign stops grouped into 127 three-stop adventures. That dataset is intentionally kept stable so BBB catalog changes do not silently rearrange current adventures or reward history.

The whole-passport counter may include stamps outside that campaign snapshot.

Shared state & rewards

Supabase stores the shared current adventure, each player's campaign progress, revealed reward history, and payout state.

An adventure completes only when both players have all three stamps. The second player receives one hidden random 20–100 L$ prize per jointly completed adventure, with the first player as sponsor. The prize is persisted once revealed and accumulates in the recipient's reward balance.

The player-facing Adventures page deliberately keeps technical status and payout setup out of the header. The exception is the large passport stamp counter out of 382 in the top-right, because completing the passport is the main goal of the game. When Adventure Treasure is enabled, the reward panel presents only the second player's treasure in friendly game language.

All reward administration lives on Admin: the Adventure Treasure on/off switch, player-name setup checks, browser payout alerts, notification testing, an admin-only 1,000 L$ test-money simulation, the optional Second Life Pay shortcut, the optional backend Second Life IM messenger, current amount owed, and the fixed 1,000 L$ manual-payment record.

The browser must allow Notifications for payout alerts to appear. The optional Firestorm Pay shortcut may also require allowing an external-app launch when the browser asks.

The admin test-money control is deliberately separate from real rewards: adding 1,000 L$ of test money changes no adventure history, no real reward balance, and no L$. The test payout alert explicitly names the Second Life username that would be paid.

The optional Second Life IM messenger is fully backend-managed for players: no prims, no LSL, no HUD, and no in-world setup. A dedicated scripted-agent avatar runs on the owner's VPS and sends the payer a real SL IM when a payout is ready.

The background threshold check runs every five minutes through Supabase cron and also after app state writes. Real payout alerts are paused while Adventure Treasure is off. The Linden API key used for the optional username-to-UUID lookup is used only for that lookup and is not stored.

Private settings

Only the private StaFi links are encrypted in the browser before being stored in Supabase. The shared Secret Club Code derives the decryption key and is not stored in the database. The two actual SL usernames and the default tab are non-sensitive shared display settings and sync separately.

The current private game architecture supports exactly two players. Non-sensitive display settings (player/tab names and default tab) are stored with shared board state so they sync without a secret. StaFi links remain encrypted and require manually entering the same Secret Club Code on each trusted device.

BBB catalog mirror

The BBB Stops page checks the public BBB catalog whenever that page opens. A Supabase Edge Function fetches and parses the BBB source, returning current stop locations and available images.

Matching stops refresh their public location/image information. Those same original BBB location photos are reused beside stops on both the Adventures page and the BBB Passport Stops page, including selected/nearby stop views. The backend keeps a shared catalog cache so pages do not have to wait on the slower BBB site every time they open. Newly discovered stops can appear as BBB Live catalog entries without changing the 127 existing adventures.

Both the stop page and the current-adventure page use a shared Second Life grid-map component. It loads Linden Lab map tiles at multiple zoom levels, supports drag/zoom, and can move from local region detail to a broad world view. Mouse-wheel zoom is debounced to avoid request bursts, and unavailable tiles are retried once before falling back to a clean placeholder instead of a broken-image box.

StaFi passport progress

Each player's personal BBB StaFi page can be saved privately. The app is designed to use those pages for passport progress, but automatic personal StaFi stamp importing is still a separate integration until it is fully connected and tested.

Feedback system

The Comments & Bugs page stores public feedback in Supabase. There is no user account list yet, so people choose any display name they want.

Anyone can submit feedback, but only the site owner has the separate Owner Passphrase used to edit, resolve, hide, reopen, or permanently delete entries. The Owner Passphrase is not stored in the public site source; only a one-way hash is stored server-side.

Users should never post Secret Club Codes, Owner Passphrases, or private StaFi links there.

Future public multi-user roadmap

The public version should keep the low-friction feel while replacing shared browser state with real user identity and group-scoped data.

  1. Add lightweight Supabase Auth: magic-link or one-time-code sign-in, with a profile/display name. No need for traditional passwords.
  2. Create Clubs: one user creates a club/pair/group and invites others with a simple invite link or short join code. A user can belong to more than one club.
  3. Make all game state club-scoped: current adventure, adventure history, reward rules, payouts, and settings belong to a club rather than one global row.
  4. Make stamp progress user-scoped: each member gets their own passport progress records. StaFi links remain private to that user; the club only needs the resulting stamp state.
  5. Use RLS everywhere: Supabase policies should allow users to see/change only their own profile data and clubs they actually belong to. Club owners/admins get explicit moderation permissions.
  6. Add live collaboration: subscribe to club state changes so adventure progress updates instantly across members' devices.
  7. Generalize rewards: move KK/AA-specific ownership into configurable club rules: who receives the prize, who sponsors it, the reward range or fixed amount, and whether everyone or selected members must complete a run.
  8. Migrate this prototype: preserve the existing AA/KK history by converting it into the first club, keeping completed adventures and payout records intact.
  9. Harden public features: rate-limit feedback/invites, add basic abuse controls, and eventually replace the temporary Owner Passphrase with authenticated owner/admin roles.

The shared public BBB catalog should stay global/read-only; private passport progress and club gameplay should stay isolated per user and club.

Current boundaries

  • The app does not automate Linden-dollar transfers. Real payments are made manually in Second Life, and all payout controls live on the Admin page rather than the player-facing Adventures screen.
  • The public BBB mirror and the private StaFi progress system are separate.
  • Feedback submission is public, but curation is owner-only through a separate private Owner Passphrase.
  • Nearby-stop ranking is best-effort until complete grid-wide coordinates are available.
  • The personal two-player reward model can be generalized later without changing the basic adventure engine.
  • Owner-only moderation is code-based rather than account-based: anyone who possesses the private Owner Passphrase would have curator rights, so that code must remain private.
Living documentation: whenever the app changes in a meaningful way, the user instructions and this architecture section should be updated in the same development pass so the site remains its own reference manual.
